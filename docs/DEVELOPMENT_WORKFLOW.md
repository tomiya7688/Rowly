# IssueとAI共同開発の運用

この文書は、Rowlyの実装者・レビュー者が、別のAIや別の会話へ作業を引き継ぐための共有手順です。共通ルールの入口は [`AGENTS.md`](../AGENTS.md) です。AI製品ごとに役割を固定せず、Issueごとに実装者とレビュー者を記録します。

## 優先度と着手状態

| ラベル | 意味 |
| --- | --- |
| `priority:P0` | 進行中のデータ損失・重大な権限迂回など、通常作業より先に対応する緊急修正です。 |
| `priority:P1` | 共通基盤、安全性、必須検証、リリース判定を進める作業です。 |
| `priority:P2` | 依存する基盤が揃った順に進める製品機能です。 |
| `priority:P3` | 追加機能、調査、文書の作業です。既存のバージョン採用方針を変更するラベルではありません。 |
| `status:ready` | 目的・範囲・受け入れ条件があり、最初の実装単位を開始できます。 |
| `status:needs-audit` | 既存実装・統合履歴・未決事項を確認し、残件を特定する調査から始めます。 |
| `status:blocked` | 本文に記載した依存の必要契約・検証が揃うまで、本体実装を待ちます。独立した調査やfixture準備は進められます。 |
| `status:in-progress` | 着手記録を残した担当者が実装しています。 |
| `status:review` | 関連PRのレビュー・CI確認・修正を進めます。 |
| `status:tracking` | 親仕様として子Issueと受け入れ条件の対応を追跡します。親Issueを一括実装しません。 |

各Open Issueには優先度と状態を一つずつ付けてください。状態を変更するときは古い状態ラベルを外してください。優先度と状態の変更理由をIssue本文へ反映してください。初回の全件整理は [`ISSUE_PRIORITIES.md`](ISSUE_PRIORITIES.md) にありますが、着手時にはGitHubの最新状態を優先してください。

依存は「Issue番号」だけでなく、利用するAPI・保存形式・必要なテストを記載してください。依存先全体が未完了でも、必要な契約がmainへ統合され、検証証拠を依存元へ記録できれば着手状態を更新できます。相互依存がある場合は、共有型・契約、core実装、adapter接続、GUI、必須ゲートへ分割してください。

## Issueを実装可能にする

実装Issueには、問題と目的、対象範囲、対象外、依存、コードとテストの入口、受け入れ条件、検証方法を記載してください。初見の実装者が「最初に何を変更し、どの結果で完了とするか」を判断できる粒度にします。

既存コードがあるIssueでは、再実装前に受け入れ条件ごとに「統合済み・ローカルのみ・未実装・未確認」を記録してください。コードの存在やIssueのClosedだけを完了証拠にせず、対象main SHAとテストを照合してください。

親Issueには子Issueへのリンクと残る受け入れ条件を記載してください。部分PRには `Refs #親番号` を使い、全体を満たさない親Issueへ `Closes` を付けないでください。子Issueを閉じる場合も、子Issue自身の全受け入れ条件を満たしてください。

## 着手と競合防止

1. 実装者はmain、対象Issue、関連PR、手元のdirty差分を確認してください。
2. 実装者はIssueへ次の着手記録を残し、状態を `status:in-progress` へ変更してください。投稿権限がないAIは、同じ本文を利用者へ返してください。
3. 実装者は投稿後にIssueを再読し、同時着手がないか確認してください。着手コメントは排他ロックではありません。競合する担当がいる場合は、編集範囲を調整してから実装してください。
4. 別checkoutで実装する場合は `kadoka/issue-<番号>-<内容>` をbranch名の既定にしてください。既存作業を引き継ぐ場合は、そのbranchと差分を維持してください。同一checkoutを複数AIが使う場合はbranchを切り替えず、重なるファイルを同時編集しないでください。
5. remote更新の直前にもbase branchとIssue本文を再確認してください。変更があれば差分を確認してから、自分の変更だけを反映してください。

```text
担当者 / 使用ツール:
役割: 実装 / レビュー / 調査
Issue / PR:
branch / base SHA:
編集するファイル・module:
最初の実装単位:
依存の充足証拠:
検証予定:
重複着手・既存dirty差分の確認結果:
```

担当交代時は元担当の引継ぎ記録を確認してください。無応答だけを理由に他者の未コミット差分を削除しないでください。所有者を確認できない差分が編集範囲と重なる場合は、所有者と引継ぎ範囲を利用者へ確認してください。

## AI別の入口

| 利用環境 | 読ませる資料と確認方法 |
| --- | --- |
| Codex | ルートの `AGENTS.md` を入口にします。ローカル `AGENTS.override.md` がある場合は、overrideからも共有 `AGENTS.md` を明示して読みます。 |
| Claude Code | `CLAUDE.md` の `@AGENTS.md` importから共通ルールを読みます。実際に読み込んだ資料を確認してください。 |
| GitHub Copilot | `.github/copilot-instructions.md` から共通ルールを案内します。環境ごとの参照表示で指示が使われたか確認してください。 |
| 通常のClaude Chat / ChatGPT | `AGENTS.md`、対象Issue、対象base SHA、関連コード・テスト・設計節を会話へ渡してください。リポジトリ全体の自動読込を前提にしないでください。 |

各AIは、参照できた資料・base SHA・変更可能な範囲を着手時に報告してください。資料を読めない場合は、その資料が必要な判断を未確認として扱い、内容を推測しないでください。個々のAIの非公開メモリやローカルレビュー基準だけに、共有する必須条件を置かないでください。

通常のチャットへ渡す依頼文には、次の項目を含めてください。機密・認証情報・無関係な大きいログは含めないでください。

```text
Rowly Issue #<番号> を担当してください。
役割: <実装 / レビュー / 調査>
base SHA: <コードを取得したcommit>
最初に添付のAGENTS.mdと共有文章・コーディング規約を読んでください。
目的・対象範囲・対象外・受け入れ条件: <Issue本文>
関連する追加決定: <コメントURLまたは本文>
参照する実装・テスト・設計節: <今回必要な資料>
既存PR・ローカル変更: <所有者と状態>
期待する成果物: <差分 / レビュー指摘 / 調査結果>
終了時に検証結果・未確認事項・次の作業を返してください。
```

## 検証・レビュー・完了

機能変更では最小の関連テストから始め、CIで必要なformat、Clippy、build、testを確認してください。具体的なコマンドと配布物検証は [`CI.md`](CI.md) と [CI定義](../.github/workflows/ci.yml) を参照してください。文書だけの変更ではリンク、参照先、テンプレートの必須項目、文章と事実の一致を確認してください。

レビュー担当は、実装担当の説明に加えて差分と根拠を確認してください。別のAIを使ったことだけで独立レビューの合格証拠にしないでください。懸念・指摘がない場合も、確認した範囲と未確認の境界を残してください。

GUI Commandを追加・変更する場合は、Registry、enabled context、Alt KeyTips経路、dialog内のkeyboard操作を確認してください。#200の自動検証と #201の専用CIゲートが完成するまでは未実装のゲートを成功扱いにせず、既存テストと実操作の確認結果を記録してください。

PRにはIssueの受け入れ条件と証拠の対応を記載してください。必須CI失敗や安全性・正しさの未解決懸念があれば承認しないでください。mainへの統合、全受け入れ条件、必要なCI・GUI実操作・配布検証を確認してからIssueを閉じてください。親Issueは子のmergeだけで閉じず、親の未分割要件も確認してください。

## PR・自己レビュー・merge

作業が一区切りしたら、実装者は次の順序でPRを完了してください。Claude、Codex、ChatGPT、Copilotのどれが実装しても、同じ手順を使います。

1. 実装者は `git fetch` を実行し、作業branchをmain最新へ追従させてください。fast-forwardで取り込めない場合は、他者の差分を壊さない方法を選び、結果をPRへ記載してください。
2. 実装者は、変更に対応する `コーディング規約.md` と `AI_WRITING_RULES.md` の項目を確認し、format・Clippy・build・testを実行してください。実行できなかった検証は、理由を添えて未実行と記載してください。
3. 実装者は、一つの独立した変更だけを含むPRを作成してください。PR本文には、Issueの受け入れ条件と証拠の対応、実行した検証、未確認事項を記載してください。親Issueの一部だけを満たす場合は `Refs #番号` を使ってください。
4. 実装者は、PRのrequired CIが完了するまで確認してください。失敗した場合は、原因をログで特定して修正し、同じPRへ追加してください。
5. 実装者は、PR差分を自分で読み直して自己レビューしてください。確認する項目は、受け入れ条件との一致、CSV正本の保護、application/process境界、利用者に環境構築を求めないこと、コーディング規約、文章の単独読解、テストの網羅です。確認した範囲と未確認の範囲をPRコメントへ残してください。
6. 次の三条件がすべて成立する場合に限り、実装者はPRをsquash mergeできます。三条件は、required CIがすべて成功していること、自己レビューに未解決の懸念がないこと、他の担当者の未解決レビューやdirty差分との競合がないことです。
7. mergeした後、実装者はmain最新を取得して関連Issueの状態を更新してください。Issueの全受け入れ条件を満たさない場合は、Issueを閉じないでください。

自己レビューは、AI自身の評価だけで合格にしません。各確認項目に、差分の該当箇所、実行したコマンドとその結果、CIの結果のいずれかの根拠を付けてください。根拠を付けられない項目は未確認として扱い、mergeせずに利用者へ報告してください。

## 引継ぎ記録

```text
Issue / PR / 担当者 / 使用ツール:
branch / base SHA / 現在HEAD:
完了した受け入れ条件と証拠:
変更したファイル:
未コミット差分と所有者:
実行したコマンドと成否:
未実行・失敗した検証と理由:
未決の仕様・依存・懸念:
次の最小作業:
次の担当者と調整状況:
```

引継ぎ時に受け入れ条件、関連コメント、検証出力を特定できるリンクを添えてください。ローカル `CONTEXT_PACK.md` を使う場合も、他者が読む必要のある引継ぎ事項はIssueやPRへ転記してください。
