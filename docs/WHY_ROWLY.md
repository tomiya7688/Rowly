# 何故Rowly？

> # **RowlyはExcelをこの世から消し去る。**

これは冗談でも、遠回しな目標でもありません。

Rowlyは、**Excelを使わなくて済むようにするためのソフトウェア**です。

Excelが担ってきた表データ編集の便利さは引き継ぐ。  
しかし、Excelを使いたくなくなる原因まで引き継ぐつもりはありません。

CSVを正本のまま、表計算・計算・自動化・履歴・Import / Export・プロジェクト管理まで完結させる。

Excelを「代替できること」を目標にするのではありません。

**Excelを開く理由を無くす。**  
その結果として、Excelをこの世から消し去る。

Rowlyは、そのために作っています。

Excelは強力です。  
セル選択、コピー、貼り付け、Sort、Filter、Undo / Redo。表を扱う道具として何十年も磨かれてきた操作性には学ぶものがあります。

でも、Excelのデータモデルまで真似する気はありません。

むしろ、**Excelを使いたくない理由のかなり大きな部分が、そのデータモデルにあります。**

## セル結合でデータや数式が消えるのは、さすがにゴミすぎる

複数のセルに値や数式が入っている状態でExcel型のセル結合をすると、左上以外の内容を捨てることがあります。

見た目を一つにしたいだけなのに、なぜデータを消す必要があるのでしょうか。

Rowlyでは、そんなことはしません。

```text
CSV
東京
東京
東京
```

これを一つのセルのように見せたければ、Viewでそう描画します。

```text
View
┌──────┐
│ 東京 │
│      │
│      │
└──────┘
```

でも、CSVは最後までこうです。

```text
東京
東京
東京
```

**見せる用とデータは別に決まっています。**

見た目のために値を消す必要はありません。  
結合のために空文字を作る必要もありません。

> **データは結合しない。見た目だけをまとめる。**

## 数式は値じゃない

Excelは、セルに数式を直接突っ込みます。

```text
=B2*C2
```

**何をしているんですか。数式は値じゃない。**

数式は計算規則です。  
値は計算結果です。

この2つを同じセルの「中身」として扱う時点で、データとロジックを混同しています。

**Excelは100年前に取り残されています。**

**数式を値扱いしてセルへ直接押し込むのは、データ処理とは言いません。**

データとロジックを同じ箱へ突っ込んで、どっちなのか分からなくしているだけです。

セルを見ないと値なのか式なのか分からない。  
式を消せば答えも消える。  
コピーすればロジックまで付いてくる。  
その状態を「セル」と呼んで全部まとめて扱う。

**そんなものはデータモデルではありません。**

セルは値を持つ場所です。  
式は、その値をどう求めるかを定義するものです。

**値と式を混ぜるな。**

Rowlyでは絶対に混ぜません。

```text
Edit  = 式・規則・割当を編集する
View  = 評価した答えを見る
Code  = CSV正本の生テキストを見る / 直接編集する
```

数式をセルへ割り当てることはできます。  
ただし、その式をCSVの値にはしません。

計算規則はCalculation BindingとしてCSV外に持ちます。

```text
Edit
D2 = B2 * C2
```

Viewでは答えを見ます。

```text
View
D2 = 1200
```

Codeでは、CSVに本当に書かれている値だけを見ます。

通常の再計算ではCSVを書き換えません。  
答えをCSVの正本へ焼き込みたいときだけ、Materializeを明示的に実行します。

**式はEdit。答えはView。正本はCode。**

これでいいんです。

数式を値のふりをさせる必要なんてありません。  
計算ロジックをセルの中へ隠す必要もありません。

**データはデータ。式は式。混ぜるな。**

## CSVは「仕方なく使う交換形式」ではない

Rowlyでは、CSVそのものを正本にします。

CSVは単純です。

- テキストとして読める
- diffが取れる
- Gitで扱える
- PythonでもRustでもRでもシェルでも読める
- Rowlyがなくてもデータを取り出せる
- 別のアプリで編集できる

これは弱さではありません。

**強さです。**

独自の巨大なbook形式へ閉じ込めないから、データの所有権がアプリ側へ移りません。

Rowlyが壊れても、Rowlyを捨てても、CSVは残ります。

その方が当たり前だと思っています。

## 一つのファイルに全部詰め込めば便利、とは思わない

データ、式、表示設定、マクロ、履歴、UI状態。

全部を一つのworkbookへ詰め込めば、一見便利です。

でも、そのファイルをそのアプリで開かないと意味が分からないなら、ロックインです。

Rowlyでは役割を分けます。

```text
CSV
  = 正本データ

Rowly Project
  = 構成、設定、参照、Automation

View
  = 表示

Calculation Binding
  = 計算規則
```

`.rwprj` や `.rowlyx` は便利に作業するためにあります。

**CSVの代わりになるためにはありません。**

## 表示の都合をデータへ押し付けない

日付を見やすくしたい。

```text
2026-10-12
→
2026/10/12
```

先頭ゼロを隠して数値らしく見せたい。

```text
00123
→
123
```

同じ値が続くから、一つにまとめて見せたい。

全部Viewの仕事です。

表示の都合でCSVを書き換える必要はありません。

**見た目は見た目。データはデータです。**

ここを混ぜると、あとで必ず分からなくなります。

## 外部編集を「事故」と呼びたくない

CSVはRowlyだけが触るものではありません。

エディタで直してもいい。  
Pythonで生成してもいい。  
別のCSVツールで編集してもいい。  
Gitで差分を見てもいい。

Rowlyを開いている間に外部からCSVが変わることすら、異常扱いしたくありません。

Rowlyはファイルをロックして世界を囲い込むのではなく、外部変更を検知して、競合を処理し、Rowly側の変更も失わない方向を選びます。

**Rowlyだけが世界の中心ではありません。**

それでいいです。

## 30年以上やっていて、まだ自分たちを制御できないの？

Excelは30年以上あります。

なのに、斜め罫線ひとつでキーボード操作が途切れます。

外枠は触れる。  
斜め線は触れない。

**同じ罫線なのに。**

何を作っていたんですか。

**30年以上あって、斜め罫線ひとつキーボードで最後まで操作できない。**

それで「キーボード操作に対応しています」は通りません。

**対応していません。途中で投げています。**

ショートカットが少ないんじゃない。  
機能ごとに操作方法がバラバラなんです。

**30年かけて、自分たちの操作体系すら統一できていない。**

Rowlyはそんなものを完成した操作系とは呼びません。

Rowlyでは、主要操作をすべてCommandとして持たせます。

```text
cell.copy
file.save
border.set
calculation.bind
view.group_equal_values
```

Shortcutでも、KeyTipsでも、Command Paletteでも、GUIでも、同じCommandへ到達する。

**操作方法が変わっても、操作そのものは変えない。**

これが当たり前です。

## GUIとMacroで別の世界を作るな

ExcelはGUIとMacroで別の世界を作っています。

GUIで出来ることが、そのままMacroの操作にならない。  
Macro Recorderで記録しても、余計な選択状態や不要な操作までコードになる。  
結局VBAを開いて、人間が後から直す。

**それ、Automationじゃない。GUI操作の録画です。**

30年以上あって、まだGUI操作とMacro操作を一つのCommandとして扱えない。

**人間向け操作と自動化向け操作が別言語。**

何のためのMacroなんですか。

Rowlyでは、GUIとAutomationを最初から分けません。

```text
GUI
Keyboard
Command Palette
Rowly DSL
CLI
Luau
   ↓
同じCommand
   ↓
process
   ↓
CSV
```

GUI専用の秘密の操作も作らない。  
Macro専用の裏口も作らない。

**人間が出来る操作はAutomationからも出来る。Automationから出来る操作は人間にも見える。**

そこを一致させます。

## GUIだけできる秘密の操作も要らない

GUIでできることが、GUIでしかできない。

それも嫌です。

Rowlyでは、主要操作を共通のCommand境界へ集めます。

```text
GUI
Rowly DSL
CLI
Luau
   ↓
Command / process
   ↓
CSV
```

マウスでやってもいい。  
キーボードだけでもいい。  
DSLで自動化してもいい。  
CLIから叩いてもいい。

同じ操作なら、同じ意味で動いてほしい。

だからRowlyは **keyboard-first** であり、同時に **automation-first** です。

## Excelを批判することと、Excelの操作性を捨てることは別

Excelの嫌なところを捨てたいのであって、便利なところまで捨てたいわけではありません。

セル選択。  
範囲選択。  
コピー。  
貼り付け。  
検索。  
置換。  
Sort。  
Filter。  
Undo / Redo。  
キーボード操作。

こういう部分は、むしろちゃんとやるべきです。

「CSVだから簡素でいい」とは思いません。

RowlyはCSVビューアを作りたいわけではありません。

**Excelを開く理由を一つずつ潰したい。**

そのために作っています。

## XLSXは必要。でも中心には置かない

現実にはXLSXを受け取ります。

XLSXで渡せと言われることもあります。

だからImport / Exportは必要です。

でも、相互運用が必要だからといって、XLSXを正本にする必要はありません。

RowlyではXLSXを橋として扱います。

中心はCSVです。

## Rowlyが無くてもデータを取り戻せる。それが最低条件

RowlyのView設定が消えてもいい。

Calculation Bindingが消えてもいい。

プロジェクト設定が壊れてもいい、とは言いません。  
もちろん壊れないように作ります。

でも、最悪それらを全部失ったとしても、

**CSVのデータそのものまで人質に取られる設計にはしません。**

Rowlyをアンインストールしても、CSVは普通のCSVとして残る。

他のソフトで開ける。

スクリプトで読める。

それくらい当たり前であってほしい。

---

Rowlyは、CSVの単純さを守ったまま、表計算ソフトの操作性、履歴、自動化、計算、プロジェクト管理を重ねようとしています。

Excelの便利さは学びます。

でも、

- 結合のために値や数式を捨てる
- **数式を値扱いしてセルへ直接押し込む**
- 見た目の都合でデータを変える
- 独自book形式へ全部閉じ込める
- GUIだけに機能を隠す
- 外部編集を邪魔者扱いする

そういう設計まで引き継ぐ気はありません。

**Excelを再実装するのではなく、Excelを使いたくない理由を一つずつ消す。**

そして最終的には、

> **Excelを開く必要そのものを無くす。**
>
> **RowlyはExcelをこの世から消し去る。**

これをRowlyのプロダクト目標として宣言します。

それがRowlyです。
